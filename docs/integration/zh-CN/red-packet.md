# 红包对接边界：SRICH CHAT 提供通信与配置，业务仍由你们负责

SRICH CHAT 不提供红包资金与开奖业务系统。买方后端负责发起、扣费、资格、参与、每人一次、留言审核、开奖和发奖；买方网页负责展示和交互。

我们接收三类事件、通过实时连接传给网页，并把后台登记的接口地址与字段配置提供给网页。这个边界应在开发前说清，避免把“有红包配置页”误认为“接上就能发奖”。

## 事件与配置

opened、joined、settled 三类事件复用信息 Webhook。group 对应业务 activity_id；每条 event_id 标识一次事件，按原内容重试。

活动 ends_at 与信息 expires_at 含义不同：活动可以持续更久，实时提示仍有短有效期。附加字段需由运营声明，并按约定类型校验。

网站通过启动器 config 事件或 aichat.config() 读取 red_packet 配置，包含 enabled、visitor_visible、revision、endpoints 和 fields。未收到配置或配置不可用时不先画入口；已打开页面不会自动收到每次后台修改，刷新取得新版本。

## 买方提供四个接口

| 接口 | 谁调用 | 责任 |
| --- | --- | --- |
| 列表 | 买方网页 | 返回可展示活动，供晚到的页面读取 |
| 详情 | 买方网页 | 返回活动及当前会员可否参与的信息 |
| 参与 | 买方网页带自己的登录态 | 校验资格并幂等处理参与 |
| 本人结果 | 买方网页带自己的登录态 | 返回该会员的最终结果 |

客服系统不代替网站验证参与登录态，不保存参与名单，不执行业务结算。后台“检查”仅针对列表与详情进行只读形状检查。

## 消息不应替代业务结果

收到 settled 后，网页应向自己的后端读取本人结果。开始与结束展示按 group + kind 去重；参与留言是独立消息，按 seq 去重，不能把同活动的不同留言都折成一条。

金额展示沿本接口的十进制字符串规则，不能混用看板整数金额。accepted 仅表示信息收下；参与和结果以买方接口为准。

## 验收

检查配置与四个地址，测试登录与未登录状态、重复参与、不同受众、过期信息、晚到页面和开关关闭。需要把汇总留给某个会员时，可以由买方计算完汇总，再调用邮箱接口写信。
